The reframe

You don't have a state problem. You have a cache problem.

Client state

You own it. It is synchronous, it is always correct, and nobody else can change it behind your back.

Which filter is selected. Is the modal open. Draft form values.

Server state

Somebody else owns it. It arrives asynchronously, it is stale the instant it lands, and it is shared by every component that asked.

The pet list. The inventory. The current user.

useState and Redux are containers. Server state needs a cache: something that knows when data is old, who is still looking at it, and when to go get it again. That is the whole argument — everything else today is a consequence of it.

This slide is the thesis. If people only remember one thing, it should be the phrase "a store is not a cache".

The tell that you are hand-rolling a cache: you have written isLoading, isError and data as three separate useStates more than twice.

Step 1 · where we started

useEffect + axios + four useStates

Read it neutrally first — this code is not stupid, it is what everyone writes. It works on the happy path, which is exactly why it survived so long.

Point at the three setX calls in each branch: that is a state machine written by hand, in triplicate, at every fetch site in the app.

Step 1 · the bill

Six defects, and only one of them is a typo

  • Race condition. No cancellation, no AbortController — switch the filter twice quickly and the slower response wins. The list shows "sold" while the dropdown says "available".
  • No cache. Every mount refetches from zero. Two components asking for the same pets make two requests.
  • No retry, no refresh. One flaky response and the user sits on an error until they reload.
  • The error is thrown away. .catch((error) => …) never reads error — every failure becomes the same blank message.
  • The filter disappears. The early return on isLoading unmounts the <Select>, so the control vanishes on every fetch.
  • It is copy-pasted. Every new endpoint re-implements all five of the above, slightly differently.

The disappearing filter is the one that lands with non-frontend folks in the room — it is a visible product bug caused purely by how the fetch state was modelled. Demo it if you have the time.

Do not let this turn into a pile-on. Land the point: none of these are mistakes of skill, they are the cost of not having a cache layer.

Step 2 · the verdict

We bought structure. We did not buy capability.

  • It still isn't a cache. The slice holds one data array. Switching to "sold" destroys the "available" result — going back refetches from scratch.
  • Same race condition. Nothing cancels the in-flight thunk. The last fulfilled to land wins, whichever status it was for.
  • Still no retry, no staleness, no invalidation. Every one of those is code you now write inside reducers.
  • New problem: coupling. The global store now imports a reducer from a page component file.

Be fair to Redux

Redux and Zustand are not the villains here. They are excellent at client state — and we still use Zustand for exactly that, three slides from the end. They were simply never designed to be an HTTP cache.

The import from a page file is a good laugh and a real point: the data layer leaked into the view layer and the store took the blame.

Close the section with the scoreboard framing — after two rewrites, the defect list from step 1 is almost entirely unchanged.

Step 3 · TanStack Query

The entire slice becomes nine lines

No thunk. No reducer. No useEffect. The next twenty minutes are about what those nine lines quietly turned on.

Resist the urge to celebrate the line count — the room can count. The interesting claim is "and it also fixed the race condition, added a cache, added retries and added background refresh".

Flag the missing useEffect explicitly. Fetching is now a declaration, not an effect: "this component needs the pets for this status."

Concept 1 of 6

The query key is a cache address

Changing the key is the refetch. You never call a fetch function — you describe what this component needs, and the library reconciles.

['pets', 'available']
One cache entry. Its own data, its own status, its own timers.
['pets', 'sold']
A different entry. Switching between them is a lookup, not a reset.
['pets']
A prefix. Invalidating it invalidates every entry underneath.

Everything in the key must be everything the queryFn reads. That is the one rule; the ESLint plugin already in this repo enforces it.

Why the race is gone

A response is written to the entry it was requested for. When ['pets','sold'] resolves late, it updates the sold entry — which nothing is rendering any more.

Step 1 had one data variable and no way to tell which request it belonged to. Step 3 can't lose that information: it is in the key.

Call back to the demo explicitly here — this slide is the promised answer.

Mention @tanstack/eslint-plugin-query is already in our devDependencies, so the "did you put everything in the key" review comment is automated.

Concept 2 of 6 · the one everyone gets wrong

Fresh, stale, inactive, collected

FreshRendered from cache. No request will be made, for any reason.
→staleTime
StaleStill shown instantly — but a trigger will refetch it in the background.
→unmount
InactiveNo component is subscribed. The data is kept anyway, for the next visit.
→gcTime
CollectedDropped from memory. The next request is a cold load.

staleTime — default 0

How long data counts as current. Zero means "assume it changed the moment it arrived", which is why people see refetches they didn't expect. It is a correctness dial, and it is yours to set per query.

gcTime — default 5 min

How long unused data survives in memory. It is a memory dial, not a freshness one. Confusing these two is the single most common misread of this library.

Slow down here. Say the sentence: "stale does not mean gone — stale means shown instantly and checked in the background." That is stale-while-revalidate, and it is why the UI feels fast.

Anticipate the objection "so it fetches constantly?" — no: it fetches on triggers, deduped, and staleTime is how you turn that down.

Concept 3 of 6

One key, one request, no matter who asks

Deduplication

Five components mount at once and all call useFindPetsByStatus. One network request goes out. All five get the same entry and re-render together.

No lifting state up. No fetching in a parent and drilling props down purely to avoid duplicate calls.

Structural sharing

After a background refetch, the new response is compared to the old one. Unchanged objects keep their identical references.

So a refetch that returns the same 40 pets does not re-render 40 rows, and your useMemo deps stay stable for free.

This is the part that quietly deletes architecture. A lot of "we need global state" turns out to have been "we need to not fetch this twice".

This slide is aimed at anyone in the room who is about to ask "but where does the data live?" — it lives in the cache, addressed by key, and any component can ask for it directly.

Concrete example from our repo: the pet list and a future header count could both call the same hook with zero coordination.

Concept 4 of 6

When it refetches — and how hard it tries

  • Key change — a different address, so a different entry
  • Component mount — if the entry is stale
  • Window focus — they came back to the tab; show them the truth
  • Network reconnect — the laptop woke up
  • Explicit invalidation — we just changed something (next slide)

Every one of these is a switch. None of them fire while data is fresh.

Use our own config as the evidence that defaults are opinions you are allowed to overrule — we did, and the comment records why.

The throwOnError line is the bridge into the next two slides. Don't explain it yet, just point at it.

Concept 5 of 6 · the grown-up part

Errors get routed, not caught everywhere

Boundary-worthy → Error Boundary

Network failures and 5xx cannot be rendered around locally. throwOnError re-throws them so RouteErrorBoundary shows a real fallback.

Everything else → local UI

404s and validation errors stay in the component, rendered inline via useApiError. The user can act on those.

This is the slide that separates "I used useQuery once" from "we run this in production". Every request in the app inherits one error policy, written in one file.

Compare against step 1: to change error handling there, you edit every .catch in the codebase.

Concept 6 of 6

Writes tell the cache what they invalidated

That one invalidate line replaces a re-fetch action, a reducer case, and the bug where the list didn't update because someone forgot to dispatch it.

Point out the meta opt-out: this mutation renders its error inline, so it excuses itself from the global toast. Policy with an escape hatch, not policy with exceptions scattered around.

The "blunt-but-correct" comment is worth reading aloud — it's honest engineering. Invalidating by prefix is coarse and completely fine here.

Drawing the line

This does not replace your state manager

Server state moves to the cache. Client state stays exactly where it was — and in this repo that is Zustand, in eleven lines, right next to the component that uses it.

  • Cache it — anything that came from an API
  • Store it — selected filter, open modal, wizard step, draft input
  • Never — copy server data into a store "so it's easier to access"

Pre-empt the fear that this is another big migration mandate. The two layers compose: the Zustand store holds the status, the status goes in the query key, the cache does the rest.

Note the type here already comes from generated models — a natural hand-off into part 4.

Step 4 · the payoff

Now stop writing the hooks at all

674lines of typed hooks
1command: generate:api

What comes out

Hooks (useFindPetsByStatus, useAddPet), models, query-key helpers, query-options factories, plus MSW handlers and faker builders — for every endpoint in the spec, not just the ones we use today.

Emphasise mutator: customInstance: generated code still goes through our axios instance, so auth headers, base URL and interceptors stay ours. This is the objection people raise first.

mode: 'tags-split' means output is grouped by OpenAPI tag — pet / store / user — not one giant file.

Step 4 · the page we actually ship

No URL. No axios. No hand-written Pet type.

  • The type is the contract. Steps 1–3 each hand-wrote type Pet — three copies, drifting independently from the API.
  • The status union is generated. FindPetsByStatusStatusItem comes from the spec, so a typo is a compile error.
  • Keys can't drift. getFindPetsByStatusQueryKey() is generated alongside the fetch, and that is exactly what useCreatePet invalidates.

Put step 1 and step 4 on screen side by side if you can — 68 lines to 41, and the 41 has caching, retries, dedupe, background refresh and real types.

Step 4 · the part nobody expects

The spec also generates your mocks

  • MSW handlers, generated. pet.msw.ts — 131 lines nobody maintains.
  • Faker builders, generated. pet.faker.ts — shaped by the spec, so the fake data is always the right shape.
  • Frontend unblocks itself. Spec exists → hooks, types and a working fake backend exist. Backend can still be a sprint behind.
  • Same handlers in tests. Dev, unit and acceptance runs share one source of truth for what the API returns.

This is the slide that wins over anyone unconvinced by "fewer lines". Parallel work with the backend is a schedule argument, not a taste argument.

Mention enable-mocking.ts: mocking is dev-only and switchable with VITE_API_MOCKING.

Before you go and rewrite everything

Five ways to get this wrong

  • Sloppy query keys. If a value is read in the queryFn it belongs in the key. Otherwise you serve one status's data under another's address.
  • Leaving staleTime at 0 everywhere. Fine for a volatile list, wasteful for a country dropdown. It is a per-query decision, so make it.
  • Copying query data into a store. The moment you useState the response, you own the staleness again and you are back at step 1.
  • Editing generated code. src/api/generated/** is output. Change the spec or the orval config; never the file.
  • Thinking useEffect is banned. It isn't. It was just never a data-fetching tool — use it for subscriptions, listeners and imperative DOM work.

Migration order that works: new endpoints use the generated hooks; existing screens get converted when you're already touching them. Nobody has to schedule a rewrite sprint.

End on the migration line — it defuses the "so we have to rewrite the app?" question before it gets asked.

Then open the floor. Keep the DevTools panel on screen during Q&A; most questions are easier to answer by pointing at it.
