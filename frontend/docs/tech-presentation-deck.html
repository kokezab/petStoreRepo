The spine

Contract-driven development

One OpenAPI spec is the shared contract between backend and frontend. Everything else hangs off it.

Orval

Generated client from the spec

The TS API client and types are generated straight from the OpenAPI spec — no hand-written fetch code. Spec changes surface as compile errors, not prod surprises.

MSW

Mock the server from the same contract

Mock Service Worker answers real network calls with contract-shaped responses. Build without a live backend, and the same mocks run in tests.

Zod

Validate at the boundary

Generated types are compile-time only. Responses are validated + normalized at runtime — contract drift is caught at the seam, not deep in the UI.

// one spec → generated client + mocked server + runtime guard

Testing

Acceptance tests as behavior

Tests read like specifications, not implementation details — and they run end to end.

Gherkin + playwright-bdd

Given / When / Then, executable

.feature files describe business behavior; playwright-bdd drives them through a real browser. Non-devs can read the scenarios; the suite verifies real user flows.

MSW · Vitest · Playwright

One test stack, three levels

Unit and component tests against contract mocks, acceptance scenarios in Gherkin, and end-to-end runs against a real deployment — the same contract underneath all three.

// the ATDD label routes AI-authored work through these steps first — see the pipeline

Server-state & platform

Data, flags & access

TanStack Query

Client-side data & caching layer

Request dedup, caching, background refetch, cache invalidation, query-key factories. One source of truth for what the server said — no hand-rolled loading/error state.

Unleash

Feature flags

Runtime flags per environment/user decouple deploy from release — ship dark, roll out gradually, kill-switch without a redeploy. Enables trunk-based dev.

Ability seeding

Authorization on the frontend

Abilities are seeded and checked before rendering privileged UI, mirroring the backend permission model — no leaking actions a user can't perform.

OIDC · Keycloak

Standards-based auth

Auth-callback / token flow via Keycloak — no bespoke auth, the same IdP the backend already trusts.

GitHub-native AI workflow

The repo is the interface

Claude runs inside CI via anthropics/claude-code-action — the contributor needs no local setup.

claude-auto-implement

Assign an issue → get a PR

Assigning a GitHub issue is the entire trigger. Claude reads it, implements on a new branch, and opens a PR that closes the issue. An ATDD label routes it through test-first steps.

@claude in comments

Iterate in-thread

Mention @claude in an issue or PR review and the same action responds — answering or pushing follow-up commits without leaving GitHub.

e2e-deployed

Deploy → E2E → promote

On merge to main: deploy a Vercel preview, run Playwright against the real URL, and promote to production only if E2E passes.

// kickoff is an assignment, not a keystroke

Working in parallel · guardrails

Isolation & gates

git worktrees

Parallel isolated workspaces

Each task or agent gets its own working directory on its own branch, sharing one repo. Multiple streams of work run side by side — no stashing, no branch-switching, no agents stomping each other's files. The local counterpart to issue-per-branch AI runs.

Husky

Commit / push gates

Pre-commit and pre-push hooks run lint, typecheck and commitlint. Contract, types and format are enforced before code lands — CI confirms, it never discovers.

The through-line

One contract, verified all the way to prod

A single spec generates the client, mocks the server, and guards the boundary. Behavior is pinned in Gherkin, work is kicked off by assigning an issue, and nothing reaches production until real end-to-end tests pass against a real deployment.
